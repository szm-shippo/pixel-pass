# ドット絵メンバーズカード交換アプリ 要件整理

## 1. コンセプト

このアプリは、スマホ同士の近距離通信を使って、ユーザーが自分で作った「ドット絵メンバーズカード」を交換するアプリである。

3DSの「すれ違い通信」のような偶発的な出会い体験を参考にしつつ、スマホOSの制約やプライバシーリスクを考慮し、以下の2系統の交換体験を想定する。

```text
1. 知り合い・目の前の相手との明示的な交換
   → NFC / QR / 近距離P2P

2. 見知らぬ人との偶発的なすれ違い交換
   → BLEによる近距離検出
```

アプリの核は「通信そのもの」ではなく、  
**自分のカードにその日の小さな気配を載せて、近くにいる誰かと交換し、あとで思い出として見返せること**である。

---

## 2. プロダクトの方向性

### 2.1 体験の中心

ユーザーは自分専用のメンバーズカードを作成する。

カードはドット絵風のビジュアルで構成される。

カードには、固定プロフィール情報と、その日のスタンプ日記を載せる。

ユーザー同士が近くにいると、カード情報を交換できる。

交換されたカードはカード帳に保存され、カレンダーやマップで見返せる。

### 2.2 目指す体験

```text
自分のカードを作る
↓
今日のスタンプを貼る
↓
近くの人とすれ違う
↓
相手のカードを受け取る
↓
カード帳に保存される
↓
カレンダーやマップで見返す
↓
同じ人と再会すると再会記録が残る
```

### 2.3 トーン

- かわいい
- 軽い
- 安全
- 匿名寄り
- 日記的
- 収集的
- 偶然性がある
- SNSほど重くない
- 出会い系に寄せない

---

## 3. 主要機能要件

## 3.1 カード作成機能

ユーザーは自分のメンバーズカードを作成できる。

### カード表面に含める情報

カード表面は「その人を識別・記憶するための固定情報」を中心にする。

```text
・ドット絵アバター
・ニックネーム
・表示用カードコード
・好きなタグ 1〜3個
・背景
・枠
・デコパーツ
```

### カード表面に入れない方がよい情報

```text
・本名
・メールアドレス
・電話番号
・SNS ID
・外部リンク
・住所
・学校名
・勤務先
・詳細な年齢
・性別を強く前提にした情報
・恋愛 / 出会い目的の項目
```

---

## 3.2 カード裏面機能

カード裏面は「その日の状態・交換ログ」を表す場所とする。

### カード裏面に含める情報

```text
・今日のピクセルスタンプ 3〜5個
・気分スタンプ
・交換日
・交換方法
  - BLE
  - NFC
  - QR
  - その他P2P
・初交換 / 再会
・再会回数
・おおまかな交換エリア
```

### 裏面の考え方

裏面は「自由記述の日記」ではなく、  
**ピクセルスタンプで構成されるスタンプ日記**とする。

ユーザーが長文を書くのではなく、あらかじめ用意されたスタンプを選んで、その日の気配を表現する。

---

## 3.3 ピクセルスタンプ日記

自由記述の日記はリスクが高いため、基本的には定型スタンプ方式を採用する。

### 目的

```text
・不適切な文章投稿を防ぐ
・個人情報の送信を防ぐ
・出会い目的の誘導を防ぐ
・ドット絵カードの世界観に合わせる
・通信データを軽くする
・多言語対応しやすくする
```

### スタンプカテゴリ例

```text
気分：
にこにこ / ねむい / ぼんやり / わくわく / しょんぼり / そわそわ

天気・空気：
晴れ / 雨 / 曇り / 雪 / 夜 / 夕焼け / 風

できごと：
コーヒー / ごはん / 読書 / 音楽 / 散歩 / 作業 / 電車 / 買い物

発見：
猫 / 花 / 星 / 本 / 看板 / 喫茶店 / 路地 / きらきら
```

### 1日のスタンプ数

MVPでは、1日あたり3〜5個までに制限する。

### 表示例

```text
☔ ☕ 🐈 🌙
雨 / コーヒー / 猫 / 夜
```

または、アプリ独自のドット絵スタンプとして表現する。

### 自動生成文について

必要に応じて、スタンプの組み合わせから短い雰囲気文を生成してもよい。

例：

```text
雨の日、コーヒーと猫の気配。
```

ただし、文章生成は補助的な要素とし、主役はスタンプにする。

---

## 3.4 すれ違い交換機能

ユーザー同士が近くにいる場合、カード情報を交換できる。

### 交換モード

#### 1. Direct Exchange

既に知っている相手、または目の前にいる相手と明示的に交換するモード。

想定方式：

```text
・NFC
・QR
・ローカルP2P
```

特徴：

```text
・周辺に広くブロードキャストしない
・ユーザーが意図的に交換する
・知り合い同士の交換に向く
・安心感がある
```

#### 2. Pass-by Exchange

見知らぬ人と偶発的にすれ違うモード。

想定方式：

```text
・BLE
```

特徴：

```text
・近くにいる相手を検出する
・真のすれ違い体験に近い
・匿名性とプライバシー設計が重要
・バックグラウンド動作はOS制限を受ける
```

#### 3. Local Session

見つけた相手とその場で追加通信するモード。

想定方式：

```text
・Android: Nearby Connections
・iOS: Multipeer Connectivity
・BLE
・Wi-Fi系P2P
```

特徴：

```text
・カード交換後の追加データ通信に使える
・リアルタイム性が必要な機能に向く
・MVPでは必須ではない
```

---

## 3.5 カード帳機能

受け取ったカードを保存・閲覧できる。

### 表示項目

```text
・相手のカード表面
・最後に受け取ったスタンプ日記
・初交換日
・最終交換日
・再会回数
・おおまかな初交換エリア
・タグ
```

### 並び替え

```text
・最近交換した順
・初めて交換した順
・再会回数順
・タグ別
・エリア別
```

### 再会表示

同じ内部IDのカードを再度受け取った場合、再会として扱う。

```text
初交換
2回目の再会
3回目の再会
```

のように表示できる。

---

## 3.6 カレンダービュー

いつ、どのカードが交換されたかを見返せる。

### 機能

```text
・日付ごとの交換数表示
・日付ごとのカードサムネイル表示
・初交換 / 再会の区別
・その日に受け取ったスタンプ日記の表示
・自分がその日に設定していたスタンプの表示
```

### 表示例

```text
2026年6月25日

交換したカード：5枚
初交換：3人
再会：2人

・mugi
  ☔ ☕ 🐈
  2回目の再会

・pixel_kuma
  🌙 🎧 🚃
  初交換
```

### 位置づけ

カレンダービューはMVPに含める価値が高い。

位置情報を使わなくても「いつ誰とすれ違ったか」を見返せるため、比較的安全で体験価値が高い。

---

## 3.7 マップビュー

どこでカードを交換したかを見返せる。

### 重要方針

正確な緯度経度は表示しない。

位置情報はぼかす。

### 記録する位置情報

```text
・おおまかなエリア
・市区町村レベル
・駅周辺レベル
・半径300m〜1km程度に丸めた位置
・任意のエリアラベル
```

### 表示例

```text
渋谷周辺
交換カード：12枚
初交換：8人
再会：4人
```

### 避けるべき表示

```text
・正確なピン表示
・相手ごとの詳細な移動履歴
・毎回の交換場所を個人単位で時系列表示すること
・自宅や職場を推測できるような精度
```

### マップ機能の扱い

MVPでは必須ではない。

Phase 2以降で導入するのが望ましい。

---

## 4. データ設計

## 4.1 基本方針

以下の3つを分離する。

```text
Card Profile
= 誰のカードか

Daily Card
= 今日どんなカード状態か

Exchange Event
= いつ・どこで・どう交換したか
```

この分離により、カード帳、カレンダー、マップ、再会判定を拡張しやすくする。

---

## 4.2 Card Profile

カード本体の固定情報。

```json
{
  "card_id": "hash_of_public_key",
  "public_key": "base64_public_key",
  "display_card_code": "CAT-9F3A",
  "nickname": "mugi",
  "avatar_id": "cat_03",
  "frame_id": "blue_frame",
  "background_id": "night_grid",
  "tags": ["cafe", "walk", "music"],
  "created_at": "2026-06-25T10:00:00+09:00",
  "signature": "..."
}
```

---

## 4.3 Daily Card

日替わりのスタンプ情報。

```json
{
  "card_id": "hash_of_public_key",
  "date": "2026-06-25",
  "stamps": ["rain", "coffee", "cat", "night"],
  "mood": "sleepy",
  "template_version": "daily_stamp_v1",
  "signature": "..."
}
```

### 注意

スタンプ画像そのものは送らない。

交換するのは `stamp_id` の配列にする。

---

## 4.4 Exchange Event

交換イベントの記録。

```json
{
  "exchange_id": "uuid",
  "card_id": "hash_of_public_key",
  "exchanged_at": "2026-06-25T18:42:00+09:00",
  "exchange_method": "ble",
  "is_first_meeting": false,
  "reunion_count": 3,
  "location": {
    "enabled": true,
    "precision": "area",
    "label": "渋谷周辺",
    "lat_approx": 35.66,
    "lng_approx": 139.70,
    "radius_m": 800
  },
  "received_card_snapshot": {
    "nickname": "mugi",
    "avatar_id": "cat_03",
    "stamps": ["rain", "coffee", "cat"]
  }
}
```

### 方針

交換履歴はカード本体とは別に保存する。

これにより、同じカードとの複数回の交換を管理できる。

---

## 5. ID・認証・一意性設計

## 5.1 カードナンバーの扱い

サーバーレスP2Pでは、人間向けの短いカードナンバーを全世界で絶対一意にすることは難しい。

そのため、以下のように分ける。

```text
内部ID：
公開鍵ハッシュなどの長いID

表示用カードコード：
短くてかわいい飾り用コード
```

### 表示用コード例

```text
CAT-9F3A
RAIN-A7C0
MOON-42B1
```

表示用コードは被る可能性がある。

ただし、識別には使わないため問題ない。

---

## 5.2 内部ID

内部IDには公開鍵のハッシュを使う。

```text
card_id = SHA-256(public_key)
```

公開鍵は端末内で安全な乱数を用いて生成された秘密鍵から導出する。

公開鍵ベースのIDは、実用上ほぼ一意と見なせる。

ただし、数学的に絶対衝突しないわけではない。

---

## 5.3 署名検証

交換データには署名を付与する。

受信側は以下を検証する。

```text
1. public_key から card_id を再計算する
2. 受信した card_id と一致するか確認する
3. signature を public_key で検証する
4. 既存 card_id があれば再会扱いにする
5. なければ新規カード扱いにする
```

### 目的

```text
・なりすまし防止
・データ改ざん検知
・再会判定
```

---

## 5.4 緯度経度をID生成に使わない

初回登録時の緯度経度をカードID生成に使う案は採用しない。

理由：

```text
・公開鍵だけで一意性は十分高い
・位置情報を混ぜても一意性改善の必要性が低い
・初回登録場所が自宅などの個人情報になり得る
・ハッシュ化しても設計上のリスクが残る
・ユーザーに説明しづらい
```

位置情報はID生成には使わず、交換イベントの記録にのみ使う。

---

## 6. 通信設計

## 6.1 基本方針

サーバーを使わない、または最小限にする前提。

P2Pまたは近距離通信を中心に設計する。

---

## 6.2 BLE

### 用途

```text
・見知らぬ人とのすれ違い検出
・近くにいる端末の発見
・一時IDの広告
```

### BLEで送るもの

BLE広告では固定IDを送らない。

```text
・短時間だけ有効な一時ID
・サービス識別子
・必要最低限の情報
```

### BLEで送らないもの

```text
・固定カードID
・公開プロフィール全文
・ニックネーム
・正確な位置情報
・連絡先
```

### 注意点

```text
・バックグラウンド動作はOS制限を受ける
・iOS/Androidで挙動差がある
・電池消費に注意
・追跡リスクへの対策が必要
```

---

## 6.3 NFC

### 用途

```text
・知り合い同士の明示的交換
・周囲にブロードキャストしたくない場合の交換
・初回の公開鍵交換
・接続トークン交換
```

### NFCの位置づけ

NFCは「すれ違い通信」ではなく「タッチ通信」。

偶発的な出会いよりも、目の前の相手との明示的交換に向いている。

### NFCで送るもの

```text
・公開鍵
・接続招待トークン
・カードID
・小さなカード情報
・署名付きデータ
```

---

## 6.4 QR

NFCの代替手段としてQRを用意する。

理由：

```text
・NFCは端末やOSによって制約がある
・QRはクロスプラットフォームで扱いやすい
・ユーザーに説明しやすい
・初回交換に向いている
```

---

## 6.5 Wi-Fi / P2P

本格的な通信が必要な場合に使う。

### Android

```text
Nearby Connections
Wi-Fi Direct
```

### iOS

```text
Multipeer Connectivity
```

### 注意

iOSとAndroidをサーバーレスで直接P2P通信させるのは難易度が高い。

MVPではQR中心の軽量交換に限定する。Wi-Fi / P2Pは将来の拡張候補に留める。

---

## 7. プライバシー要件

## 7.1 固定IDをブロードキャストしない

BLE広告などで固定カードIDや公開鍵ハッシュをそのまま出さない。

一時IDを使う。

MVPではBLEを実装しないため、固定IDのブロードキャスト自体を行わない。

### 一時ID

```text
・短時間で変わる
・固定ユーザーIDと直接結びつかない
・受信側がP2P接続後に署名検証する
```

---

## 7.2 位置情報はぼかす

マップ機能では正確な緯度経度を表示しない。

MVPでは位置情報を要求せず、QR交換イベントにも場所を保存しない。

```text
・半径300m〜1km程度に丸める
・市区町村や駅周辺レベルにする
・「このあたり」表示にする
```

---

## 7.3 位置情報はオプトイン

位置情報記録はユーザーが明示的にONにする。

MVPでは位置情報記録機能を提供しない。

設定例：

```text
□ 交換場所を記録する
□ 正確な位置ではなく、おおまかな場所で保存する
□ 相手ごとの場所履歴は保存しない
```

---

## 7.4 相手の行動履歴を見せすぎない

特定の相手について、毎回どこで会ったかを細かく時系列表示しない。

避けるべき例：

```text
Aさん
1回目：新宿駅
2回目：渋谷駅
3回目：池袋駅
```

推奨：

```text
・初交換エリアのみ表示
・最新の交換エリアのみぼかして表示
・再会回数を中心に表示
・詳細な場所履歴は出さない
```

---

## 7.5 個人情報の送信を避ける

初期版では以下を送信不可にする。

```text
・本名
・電話番号
・メールアドレス
・SNS ID
・外部URL
・住所
・学校名
・勤務先
・正確な現在地
・画像自由添付
・ニックネーム以外の自由記述
```

今日の気分や出来事は、自由記述ではなくピクセルスタンプで表現する。

---

## 8. セキュリティ要件

## 8.1 鍵生成

初回起動時またはカード作成時に鍵ペアを生成する。

```text
・秘密鍵は端末内に安全に保存
・公開鍵は交換可能
・秘密鍵は外部に送らない
```

iOSではKeychain / CryptoKit相当、AndroidではAndroid Keystore / SecureRandom相当を想定する。

---

## 8.2 署名

送信するカードデータには署名を付与する。

署名対象：

```text
・card_id
・public_key
・card profile
・daily card
・timestamp
・schema_version
```

---

## 8.3 受信データ検証

受信側では必ず検証する。

```text
・スキーマ検証
・サイズ制限
・署名検証
・不明なstamp_idの無視
・不明なschema_versionの扱い
・危険なURLや外部リンクの排除
```

---

## 8.4 データサイズ制限

P2P交換データは小さく保つ。

MVPでは画像そのものを送らず、アプリ内定義のIDを送る。

```text
avatar_id
stamp_id
frame_id
background_id
```

のようなID中心にする。

---

## 9. 非機能要件

## 9.1 サーバーレス前提

基本的にサーバーを使わずに成立する設計とする。

理由：

```text
・運用費を抑える
・個人開発で始めやすくする
・P2Pアプリとしての特徴を出す
```

ただし、将来的な拡張として以下は検討余地がある。

```text
・スタンプ追加配信
・バックアップ
・通報
・ブロック共有
・イベント限定コンテンツ
```

MVPでは必須ではない。

---

## 9.2 オフライン動作

インターネット接続がなくても、基本機能が動くこと。

```text
・自分のカード作成
・スタンプ日記作成
・QR交換
・カード帳閲覧
・カレンダー閲覧
```

---

## 9.3 低通信量

交換データは軽量にする。

画像やファイルではなく、IDと署名付きJSONを交換する。

---

## 9.4 バッテリー配慮

BLEスキャンや広告はバッテリーに影響するため、将来実装時は制御が必要。

```text
・アプリ起動中のみ検出するモード
・イベント会場モード
・省電力モード
```

MVPではBLEを実装しないため、QR表示・QR読み取りによる電池消費を通常のカメラ利用範囲に収める。

---

## 9.5 OS制約への配慮

スマホOSではバックグラウンド通信に制限がある。

特にiOSでは、3DSのすれ違い通信のような完全自動・常時・高信頼な交換は期待しない。

MVPでは以下を前提にする。

```text
・アプリ起動中または明示的な待機状態を中心にする
・バックグラウンドはベストエフォート
・確実な交換を求める場合はNFC / QRを使う
```

---

## 10.4 MVPのQR交換仕様

MVPのQR交換は、片方向のカード受け渡しとする。

双方が交換したい場合は、お互いにQRコードを読み取る。

```text
・QRにはCardProfileと当日のDailyCardを含める
・QRにはschema_versionを含める
・QRには署名を含める
・QRには位置情報を含めない
・QRに有効期限は設けない
・スクリーンショット経由でも読み取り可能にする
・受信側は読み取り時点の全文スナップショットとして保存する
・交換イベントの日付は受信端末の時刻で記録する
```

後から相手がニックネーム、アバター、スタンプなどを変更しても、保存済みカード帳には受信時点の見た目を残す。

---

## 10.5 MVPのエラー・例外系

```text
・QR読み取り失敗: 再スキャンできる
・未対応schema_version: 保存しない
・署名検証失敗: 保存しない
・必須項目不足: 保存しない
・データサイズ超過: 保存しない
・自分のcard_id: 保存しない
・ブロック済みcard_id: 保存しない
・今日のスタンプ未設定: スタンプなしのカードとして読み取り可能
・端末時刻ずれ: MVPでは厳密に検出しない
```

同じQRを何度読み取っても、自動では重複排除しない。既に受け取り済みのcard_idは、保存前に再会として記録することを表示する。

MVPで要求するOS権限は最小限にする。

```text
必要:
・カメラ: QR読み取り
・写真保存: SNS共有画像を保存する場合のみ

不要:
・位置情報
・Bluetooth
・NFC

```

カメラ権限を拒否された場合でも、カード作成、自分のQR表示、カード帳、カレンダーは利用できる。

## 10.7 MVPのデータ保持・削除

MVPではすべてのデータを端末内に保存する。

```text
・自分のカードプロフィールは端末内に保存する
・受信カードは全文スナップショットとして保存する
・交換履歴はExchangeEventとして端末内に保存する
・クラウド同期、バックアップ、エクスポートはMVP外
・アプリ削除時は全データが失われる
・受信カードを削除できる
・受信カードを削除すると、そのcard_idに紐づく交換履歴も削除する
・削除後に同じ相手を再度読み取った場合、ローカル履歴がなければ初交換扱いにする
・自分のカードは編集できるが、内部IDは変えない
・自分の内部IDリセット機能はMVPでは提供しない
```

## 10.8 MVPの安全要件

自由記述はニックネームのみとする。

```text
・今日の気分や出来事はスタンプで表現する
・タグは定型タグから選択する
・外部リンク、SNS ID、連絡先、自己紹介文は作らない
・ローカルブロックを提供する
・ブロックしたcard_idは再読み取りしても保存しない
・ブロック情報は端末内のみで保持する
・ブロック情報は相手に通知しない
・削除とブロックは別機能にする
```

---

## 10.9 MVPの計測方針

MVPでは外部分析SDKを入れない。

```text
・端末外への自動送信はしない
・初期検証はクローズドテストの観察、ヒアリング、任意アンケートで行う
・アプリ内にはユーザー自身が見るためのローカル統計だけを持つ
・ローカル統計例: 交換回数、初交換人数、再会回数、今月の交換数
```

---

## 10.10 MVPの課金方針

MVPでは課金を実装しない。

```text
・アプリ内課金なし
・すべてのMVP基本機能は無料
・購入復元、有料アイテム所有状態、ストア課金処理は実装しない
・デコ課金、スタンプパック、カードスロット追加、サブスク、イベント主催者向け課金は将来検討
```

将来課金を見越して、asset_id、stamp_id、frame_idなどのID体系は維持する。

## 16. プラットフォーム戦略

## 16.1 基本方針

開発の主軸はiPhone向けにする。

ただし、ユーザー体験を考えると、将来的にはiPhoneとAndroidで相互にカード交換できる必要がある。

そのため、MVP時点から以下を共通仕様として設計する。

```text
・CardProfile JSON
・DailyCard JSON
・ExchangeEvent JSON
・署名方式
・card_id生成方式
・stamp_id体系
・QR交換ペイロード
```

通信方式はOSごとに差分が出てもよいが、交換するデータ形式は共通にする。

---

## 16.2 iPhone向け開発を先行する理由

```text
・開発対象を絞れる
・最初のUI/UX検証がしやすい
・Appleプラットフォーム内ではMultipeer Connectivityが使える
・カード作成体験やカレンダー体験を先に磨きやすい
```

MVPでは、通信方式の完全性よりも、以下を優先する。

```text
・カード作成が楽しいこと
・スタンプ日記が続けやすいこと
・交換後にカード帳を見返したくなること
・QR交換が確実に成功すること
```

---

## 16.3 クロスプラットフォーム対応の基本方針

iPhoneとAndroidの相互通信は、最初から完全P2Pで実現しようとしない。

まずはQRコードを共通の交換方式として扱う。

### MVPでの確実な相互通信

```text
iPhone ↔ iPhone
→ QR
→ 将来的にMultipeer Connectivity

iPhone ↔ Android
→ QR

Android ↔ Android
→ QR
→ 将来的にNearby Connections
```

---

## 16.4 通信方式ごとの位置づけ

### QR

最も堅いクロスプラットフォーム交換方式。

```text
・iPhone / Android両対応しやすい
・OSの近距離通信制限を受けにくい
・実装が軽い
・ユーザーが理解しやすい
・サーバー不要
・公開鍵交換に向いている
```

MVPではQRを主軸にする。

### NFC

知り合い同士、または目の前の相手と明示的に交換する補助方式。

```text
・ブロードキャストしたくない場合に向く
・タッチ通信として分かりやすい
・端末やOSによる差分がある
・QRの代替または補助として扱う
```

MVPでは実装しない。将来の明示的交換手段として検討する。

### BLE

見知らぬ人との偶発的なすれ違い検出に使う。

```text
・真のすれ違い体験に近い
・iOS / Androidで挙動差がある
・バックグラウンド動作はベストエフォート
・固定IDを出さない設計が必須
```

MVPでは実装しない。将来のすれ違い体験の検証対象として扱う。

### Multipeer Connectivity

iPhone同士の近距離P2P通信に使う候補。

```text
・Appleプラットフォーム内では相性が良い
・Androidとの相互通信には使えない
・iPhone同士の追加通信や近距離交換に向く
```

### Nearby Connections

Android同士の近距離P2P通信に使う候補。

```text
・Android同士の発見、接続、データ交換に向く
・iPhoneとの相互運用は主軸にしない
```

---

## 16.5 推奨フェーズ

### Phase 1: iPhone版MVP

```text
・iPhoneでカード作成体験を作る
・QR交換を実装する
・カード帳を実装する
・カレンダーを実装する
・署名検証と公開鍵ベースIDを実装する
・NFC / BLE / Local P2Pは実装しない
```

### Phase 2: Android版追加

```text
・同じデータ形式をAndroidで実装する
・QR経由でiPhoneとAndroidのカード交換を成立させる
・Android側ではNearby Connectionsを検証する
```

### Phase 3: クロスプラットフォームBLE検証

```text
・iPhone ↔ AndroidでBLEすれ違いを検証する
・アプリ起動中を前提にする
・固定IDを広告しない
・一時IDのみを広告する
・詳細情報は接続後に署名付きで交換する
```

### Phase 4: OS別P2P最適化

```text
iPhone同士：
Multipeer Connectivity

Android同士：
Nearby Connections

iPhone ↔ Android：
QR / BLE / 必要ならローカルネットワーク通信
```

アプリのプロトコルを通信方式に依存させない。


## 18. マネタイズ戦略

## 18.1 基本方針

初期から強く課金しない。

このアプリはネットワーク効果が重要なので、交換やカード帳の基本機能に課金壁を置くとユーザー数が増えにくくなる。

基本方針は以下。

```text
交換・カード作成の基本体験は無料
↓
見た目・記録・イベント機能で課金
↓
コミュニティやイベント向けにB2B課金
↓
将来的にプレミアム機能を追加
```

---

## 18.2 やってはいけない課金

### 交換機能を有料にする

```text
NG:
カード交換は有料
すれ違い回数に制限
1日3回以上交換するには課金
```

交換を制限するとネットワーク効果が壊れる。

### 受け取ったカード閲覧を有料にする

```text
NG:
受け取ったカードを見るには課金
カード帳の基本閲覧が有料
```

交換後の満足感を削るため避ける。

### 出会い系に寄る課金

```text
NG:
近くの人をもっと探せる有料機能
異性を優先表示
相手の詳細情報を見られる
正確な位置が見られる
```

安全面・審査面・ブランド面で避ける。

## 20. 最終まとめ

このアプリは、以下の体験を提供する。

```text
自分だけのドット絵メンバーズカードを作る
↓
今日の気分や出来事をピクセルスタンプで表現する
↓
近くの人とカードを交換する
↓
カード帳に保存する
↓
カレンダーやマップで思い出として見返す
↓
同じ人と再会すると記録が育つ
```

MVPでは、以下を優先する。

```text
・iPhone向け開発
・カード作成
・ピクセルスタンプ日記
・QR交換
・カード帳
・再会判定
・カレンダー
・SNS共有画像
```

Android対応やBLEすれ違いの本格化は段階的に進める。

NFC、マップビュー、イベント機能、課金はPhase 2以降に回す。

最も重要な設計原則は以下。

```text
・通信よりも、交換されるカードの魅力を主役にする
・安全性を優先し、自由記述や個人情報共有を避ける
・位置情報はぼかし、ID生成には使わない
・サーバーレスでも成立するように、公開鍵ハッシュと署名を使う
・iPhone先行でも、データ形式は最初からAndroid互換にする
・MVPではQRを確実なクロスプラットフォーム交換方式にする
・マーケティングは全国展開ではなく、小さな場所で交換密度を作る
・MVPでは課金を実装せず、将来的に見た目・イベント・記録機能で収益化を検討する
```
